# 长时间运行检查（2026-09-15）

> 本文下方数值为加入 RR 之前的 HR 单项基准。当前双指标容量与验证边界见 [RR 验证说明](RESPIRATORY_RATE_VALIDATION.md)。

## 结论与适用范围

默认按连续 24 小时、每 5 分钟记录一次评估。已完成源码负载审查、整机当前负载采样和合成数据容量 / 定时测试；尚未进行真实摄像头连续 24 小时或多日耐久试验。因此建议按天 / 病例有人值守使用，不能据此承诺 24×7 无人值守或确定的 OCR CPU 百分比。

## 本机观察

- 硬件读取：Mac16,12，24 GiB 内存，10 个逻辑 CPU。
- 12:03:18–12:03:20 的两个整机采样：CPU 空闲 78.30% / 81.68%，即整机使用约 21.70% / 18.32%。这是全部应用的瞬时负载，不是本页面或摄像头 OCR 的独立负载。
- `top` 显示约 22 GiB 已使用、约 1.6 GiB 未使用，其中压缩内存约 5 GiB；`memory_pressure -Q` 报告系统可用百分比 63%。这些统计口径不同，不能直接将“已使用 22 GiB”判定为即将耗尽，也不能把它当成本应用占用。
- 只读电源设置显示：电池和接电配置的空闲 sleep 为 1 分钟，displaysleep 为 0。有效的应用常亮断言可能阻止空闲休眠，但页面不能保证系统不会释放它；本轮未更改系统电源设置。

## 已修复的问题

1. 记录表原先在每次父组件更新时遍历全部历史记录，并为每个时间单独新建日期格式化器。现在每页至多 50 行、默认跟随最新页，并复用格式化器；保留历史翻页 / 修订和全量导出 / 打印。
2. 所选文件夹原先每 5 分钟增加一个全量 CSV，累计保存的总行数随运行时间呈平方级增长。现在每个病例 / 会话使用一个固定完整 CSV，通过 `createWritable` 写入并关闭后更新，减少重复磁盘数据。下载模式保持带时间戳的新文件；长期使用应选文件夹。
3. 草稿原先为每条 HR 记录保存七个未启用指标的完整空对象。现在只省略与默认值完全相同的字段，仍保留每项原始时间戳；加载时无损恢复。历史有效读数、原因和额外字段不会被当成空数据删除。较大草稿提前提示归档。
4. OCR 初始化失败原先会永久缓存失败 Promise，后续尝试无法恢复；现在允许后续重试，并释放参数配置失败或停止之后才初始化完成的 Worker。

当前 OCR 串行执行，每轮完成后等待约 1.2 秒；趋势历史最多保留 120 条，识别共识候选最多 3 条，没有无限增长的识别任务队列。会话记录和人工审计仍随使用增长，需定期归档。

## 合成容量结果

使用项目自己的快照、CSV、持久化、记录表组件生成模拟 HR=118 的演示数据。时间范围包含起点，因此行数为 `天数 × 288 + 1`。不含真实病例或视频。草稿大小使用序列化字符串字符数 × 2 的保守 UTF-16 口径，浏览器实际计费口径可能不同。

原版记录表静态渲染在本机单次样本分别约 44 / 154 / 683 ms；优化后单独测试样本约 8 / 2 / 5 ms，主要来自只渲染当前页及复用格式化器。不同页行数和系统负载影响结果；这是 Node/React 静态渲染基准，不是 Chrome 帧率，也不包含视频解码、摄像头、WASM OCR 或 GC 耐久表现。

另以模拟时钟验证一天内 288 个五分钟截止点，均触发保存，最终 289 行时间槽唯一且完整。文件写入使用 mock；文件夹授权、实际磁盘写入和整机休眠不在该模拟测试范围内。

## 使用建议

- 接电，保持页面在前台，避免合盖、锁屏和电脑休眠，确认“屏幕常亮中”。不要单凭开着浏览器就认为采集在继续。
- 选择本地保存文件夹，首次实际检查 CSV 内容与文件修改时间；每次刷新重新授权目录。
- 按天 / 病例导出 CSV 和审计 JSON 后再新建病例；新建前确认文件确实已写入。较长会话和其他同域应用会共享浏览器存储额度。
- 正式长时间使用前，用目标摄像头、分辨率和监护仪完成至少一轮目标时长的试运行，观察温度、页面响应、缺失槽、保存时间和内存趋势。此项本轮未完成。

浏览器依据：[Web Storage 配额](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)、[Screen Wake Lock 的释放条件](https://developer.chrome.com/docs/capabilities/web-apis/wake-lock)。
