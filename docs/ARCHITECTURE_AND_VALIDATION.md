# PetOR Monitor 架构、调研与验证边界

> 更新日期：2026-08-18
> 定位：监护仪屏幕 HR 的摄像头 OCR **辅助转录工具**，不是生命体征测量设备、独立报警器或电子病历系统。当前只支持心率；其他生命体征后置。

## 1. 现有代码审计

原仓库只有 `readnumberpa.py` 与旧 README，实现的是：

1. 从预录视频文件名推算绝对时间；
2. 每 0.2 秒跳转抽一帧；
3. 只截取左下角单个 ROI；
4. 使用 PaddleOCR `TextRecognition` 读取心率；
5. 用字符替换、`30–250` 范围和跳变阈值过滤；
6. 识别失败时沿用上一心率，最终导出 CSV。

可复用的是“按比例配置 ROI、数字纠错、宽泛可能范围、时间戳与 CSV”思路。不安全且未复用的是：

- `11 → 111` 等样本专用猜测；
- OCR 失败后静默沿用旧值；
- 用跳变阈值替换可能真实的生理变化；
- 把单个心率 ROI 当成“所有数字”识别能力。

## 2. Web 原型架构

```text
摄像头 getUserMedia（在线） ─┐
                              ├→ 冻结画面 → HR ROI → Tesseract.js
本机 MP4/MOV 媒体时间轴（离线）┘                   ↓
                         HR 解析 + 范围 + 多帧一致 + 拒识/待核对
                                                    ↓
          实时固定 5 分钟时间槽 / 离线可选媒体槽 → HR 草稿表
                                                    ↓
              简体中文复诵 + 人工修订留痕 + CSV / JSON 导出
```

在线与离线共用 HR 解析、范围校验和记录模型。在线模式每轮先冻结一张完整画面再裁剪 HR；离线模式不启动墙上时间调度器，按媒体秒生成槽位，标准模式每槽读取五个相邻帧，1 秒模式每槽读取三个相邻帧。离线抽帧必须由 `requestVideoFrameCallback`（rVFC）回调返回的 `metadata.mediaTime` 与目标媒体时间匹配后才可进入 OCR；可能捕获上一旧帧的 `requestAnimationFrame` 或定时回退已移除。浏览器不支持、回调超时或媒体时间不匹配时必须显式失败，不生成伪记录。裁剪与预处理均由本机 Canvas 完成。

SpO₂、PR、NIBP、RR、EtCO₂、FiCO₂、TEMP 的 ROI、解析器或数据字段仍可能作为实验/历史兼容代码存在，但没有接入当前产品流程，也不属于本次可验收能力。后续启用任何字段前，必须单独完成 profile、真值标注、拒识、UI、播报、导出与真机验证。

### HR 参考对比管线

```text
本机参考 CSV → BOM/列名/类型校验 → video_time_s 最近点对齐
                                      ↓
                    参考来源分类（直接 / 滤波派生 / 空 / 无效）
                                      ↓
当前视频 OCR 快照 → 排除人工修订和 low-confidence → 逐点差异 + 主指标
                                      ↓
                       页面明细 + 独立 CSV / JSON 审计导出
```

参考对比不改写原始 CSV，不将其全量写入病例 localStorage，也不做任何前值填充。默认容差是采样中位间隔的一半；本次 1 秒 CSV 因此使用 `±0.5s`。每个对比行保留参考行号、原始值、过滤值、来源质量、对齐误差、OCR 状态与是否进入主指标。

主指标只统计时间对齐、参考点非派生、OCR 状态为 `ok` 且未经人工修订的配对。报告显示 exact/±2/±5 覆盖、MAE、RMSE、Bias、最大误差、拒识与待复核；所有比率同时显示分子和分母。这些指标的名称是“与当前参考 CSV 的工程一致性”，不是临床准确率。

当前只读取 HR。监护仪 HR 显示 `---` 时，系统必须保存 `HR = null`，不得使用 PR、屏幕其他数字或前一槽 HR 替代。

HR 的 `0–200 bpm` 是含端点的 **OCR 工程捕获范围**，不是临床正常范围、诊断标准或报警阈值。后处理必须得到唯一整数候选：单字符 `0–9` 可以保留原始候选，但始终标为待核对；多个候选、小数、负数与范围外结果拒识。任何结果都不得钳制到边界、按历史值补齐数字或前向填充。

在单槽解析、多帧共识和置信度门之后，再执行跨时间槽稳定门。新候选与上一条已接受 HR 的允许差值为 `max(8 bpm, 上一条已接受 HR × 15%)`：门内候选可正常接受；首个门外候选只保存为待核对的大跳候选。只有下一连续时间槽候选与该大跳候选相差不超过 `±2 bpm`，才接受**第二个时间槽自己的候选**。两次候选不取平均，首个待核对槽不被补写或追溯改写，缺失槽也不前向填充。该规则是防止 OCR 偶发跳读的自动接受门，不是临床报警阈值。

### 已实现的拒识原则

- HR 独立保存原始 OCR、最终值、置信度、状态和捕获时间；
- 只解析唯一整数 HR 候选；0 和 200 属于范围内，负数、小数、201 及以上拒识并保留原因；
- 单字符 `0–9` 不因多帧重复就自动升级为可靠值，避免固定 ROI 持续截掉十位数；
- 同一裁剪中出现多个候选时拒绝选择，不按历史值、数值接近程度或字符串位置猜测；
- OCR 置信度低于 55% 不自动认定为可记录；
- 两次连续读数不一致时保持“待核对”；
- 超出 0–200 工程范围时拒识；超过 `max(8 bpm, 15%)` 跨槽跳变门的首个候选保留为待核对，只有下一连续槽与该候选相差不超过 `±2 bpm` 才接受第二槽自身数值；
- 大跳确认不平均两个候选、不追溯改写首个待核对槽，也不使用旧值覆盖或前向填充；
- 页面后台、摄像头中断、读数超过 15 秒或时间槽错过 30 秒时，写入缺失原因，不回填；
- 人工修订要求原因，保留旧值、新值和时间。
- 标准离线槽采用五帧 HR 共识；1 秒工程对比模式采用三帧 HR 共识。可能漏掉前导数字时保留候选但标为“待核对”，不自动写成可靠值。

### 联合用药记录边界

联合用药模块与 HR 识别管线解耦，只保存人员手工录入的事实：

- 药物目录由医院自定义，初始为空，不随产品预置默认药名；
- 一次给药事件可以包含多种药，并记录阶段与实际时间；
- 每种药保存名称、剂量文本、单位、途径和备注，剂量文本按原样保存，不解析为计算参数；
- 目录新增/删除与事件新增/编辑/删除形成带时间的审计记录；
- 用药事件随会话在浏览器本机保存，旧会话可迁移，并提供用药 CSV、审计 CSV 与 JSON 导出。

该模块不预填剂量，不按体重或其他字段自动算量，不给出推荐药物、配伍、禁忌、剂量或临床决策建议。界面上的“选择”只是在医院自定义目录中选择记录项，不代表产品建议使用该药。

## 3. 浏览器能力与部署结论

- 浏览器摄像头依赖安全上下文，即 HTTPS 或 localhost，且需用户明确授权：[MDN `getUserMedia()`](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)。
- 移动端可用 `facingMode: environment` 优先后置镜头，但实际能力必须通过媒体约束渐进增强：[MDN `facingMode`](https://developer.mozilla.org/en-US/docs/Web/API/MediaTrackConstraints/facingMode)。
- Tesseract.js 在 Web Worker/WASM 中执行，本原型裁剪 HR ROI 并限制数字字符集：[Tesseract.js API](https://github.com/naptha/tesseract.js/blob/master/docs/api.md)。Worker、SIMD/非 SIMD Core 和数字模型已按固定版本自托管、用 SHA-256 在构建时校验并由 Service Worker 预缓存；运行时不请求第三方 CDN，图像本身不上传。做法参考 [Tesseract.js 本地托管](https://github.com/naptha/tesseract.js/blob/master/docs/local-installation.md)。
- 系统语音由 Web Speech API 提供，页面只选择简体中文普通话音色，必须用户先测试成功才允许自动复诵；错误、超时或无中文音色时保留视觉降级：[MDN SpeechSynthesis](https://developer.mozilla.org/en-US/docs/Web/API/SpeechSynthesis)。
- GitHub Pages 只能托管静态前端，无法运行原 Python/PaddleOCR 服务；Pages 的 HTTPS 满足摄像头安全上下文：[GitHub Pages HTTPS](https://docs.github.com/en/pages/getting-started-with-github-pages/securing-your-github-pages-site-with-https)。
- 工作流按 GitHub 官方 Pages Actions 模式使用 `configure-pages`、`upload-pages-artifact` 和 `deploy-pages`：[GitHub 自定义 Pages 工作流](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)。
- 当前源码、工作流与文档仍是本地未提交状态，尚未 push，也没有完成当前版本的 GitHub Actions / Pages 部署；Pages HTTPS 只描述部署后的能力，不是当前已上线状态。
- Android 10+ 当前版 Chrome 与 iOS/iPadOS 17+ Safari 仅列为前台条件支持目标，摄像头、rVFC 视频抽帧、简体中文语音、分享与资源限制仍待真机验收。后台/锁屏运行明确不支持；手机 1 秒模式不保证完成时间、吞吐或一定完成。

## 4. 医疗安全与业务边界

- AAHA 指南强调电子监护与麻醉人员的直接患者评估必须结合：[AAHA 麻醉监护指南](https://www.aaha.org/resources/2020-aaha-anesthesia-and-monitoring-guidelines-for-dogs-and-cats/phase-2-day-of-anesthesia/step-4-anesthetic-protocol/)。
- ACVAA 建议麻醉中定期记录心率、呼吸率及已监测的氧合和血压，并强调持续有人负责监护：[ACVAA 指南 PDF](https://www.aaha.org/wp-content/uploads/globalassets/02-guidelines/anesthesia/8-9-16_acva_monitoring_guidelines.pdf)。
- 本原型不测量生命体征，不判定麻醉深度或心律，不关闭或替代监护仪报警，不允许无人值守，不能直接用于用药决策。
- GitHub Pages 演示页无身份认证、角色权限、可靠备份和长期归档，因此只能导出“待负责兽医复核的辅助转录草稿”。

### B. 当前真实视频验证结论

用户随后提供了一段真实 Mindray iMEC8 Vet 视频：366.931 秒、544×960 竖屏、H.264/AAC。它足以验证文件导入、竖屏 HR ROI、`00:00`/`05:00` 两个标准槽，以及“约 285 秒起 HR 横线时保持缺失，不取用其他屏幕数字”的关键安全规则。代码库仅保存去身份化的人工基准 JSON，不保存视频。

抽帧实测说明通用 Tesseract 对清晰大号 HR 已有可用基础。历史基准里对其他屏幕字段的观察只是实验性研究材料，不构成产品支持。因此该单个 6 分钟样本只能作为 HR 工程回归，**不能宣称临床识别率已经验收**。

用户又提供了一组 602.333 秒、544×960、21 fps 的 H.264/AAC 视频与 603 行旧 OCR CSV。两者的相对时间轴匹配，但 CSV 的 `filtered_value` 不是独立真值：481 行与 `raw_value` 相同，122 行为规则修正或前值回填。人工抽帧证实了该风险：230 秒附近画面在约 229.86 秒仍为 59、到 230.17 秒已变为 57，而 CSV raw/filtered 为 5/59；602.2 秒画面 HR 约 47，CSV raw/filtered 为 4/50。这 122 点默认排除出主指标，不能拿滤波值替代逐帧真值。

旧 CSV 的 603 个 `filtered_value` 均在 40–66，481 个直接点也均在 40–66；但原始列含 109 个单字符（3/4/5/7）、11 个空值和 2 个 `517`。122 个派生点中 120 个等于上一条过滤值，说明“数值在范围内且平滑”不能证明正确。第二段视频的监护仪位置更高，因此新建单独的 10:02 profile；约末段机位又向右移动 0.06 画幅，紧裁 HR 框可能只看到一位数。当前实现依靠单字符待核对门禁处理该问题，不再依赖旧的 20 bpm 下限，也不扩大框后猜值。对应的去身份基准为 [`fixtures/mindray-imec8-vet-reference-pair.json`](fixtures/mindray-imec8-vet-reference-pair.json)。

当前跨槽跳变确认门与严格 rVFC `mediaTime` 抽帧版本已在本地桌面浏览器完成 603 槽逐秒复验：`0…602` 每槽三帧，共 1,809 个 HR OCR，时间对齐 603/603。481 个直接参考点中，254 个自动接受且全部完全一致，exact、±2、±5 均为 `254/481（52.8%）`；89 个拒识、138 个待复核，122 个滤波/回填派生点排除。自动接受配对的 MAE、RMSE、Bias 和最大误差均为 0；全部 603 行的质量状态为 255 个 `complete`、339 个 `review`、9 个 `missing`。

真实跳变例验证了稳定门语义：`00:58` 的 OCR/参考均为 47，相对已接受基线 59 超过 `max(8 bpm, 15%)`，因此首槽只保留大跳候选；`00:59` 的 OCR/参考均为 45，与候选 47 相差 2，系统接受第二槽自己的 45，没有取平均，也没有反向补写 `00:58`。这组结果仅是本地桌面浏览器对旧 OCR CSV 直接点的工程一致性；参考 CSV 不是独立临床真值，结果不能外推为临床准确率，Android/iOS 真机也仍待验。

形成准确率结论仍需要：

1. 每种监护仪型号、分辨率与主题单独建立 profile；
2. 每个 profile 至少 10–30 分钟且逐秒标注 HR 的原始视频，覆盖正常、数值跳变、探头脱落、横线、报警反色、遮挡、反光和失焦；
3. 统计 HR exact match、错误接受率、拒识率与延迟；
4. 在实际固定机位完成整台手术的 shadow mode，由人员同步抄录作为金标准，软件不参与治疗决策。

### C. 生产优先项

1. 先向监护仪厂商询问 RS-232、USB、LAN/API 或标准数据接口；直连数据通常比摄像头 OCR 可靠。
2. 按监护仪型号建立 screen profile，加入屏幕四角透视校正、失焦/过曝/画面冻结检测和 HR 新鲜度。
3. 生产环境将已自托管的 OCR 资源迁入受控 HTTPS/医院内网，并对 Service Worker 更新、缓存配额和断网运行做真机回归。
4. 补充身份认证、角色权限、不可覆写审计、备份、保留/销毁策略和机构风险评估。
